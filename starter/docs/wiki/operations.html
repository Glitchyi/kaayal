Operations

Everything needed to run, wire, demo and operate Kaayal — condensed. Each section links to the canonical runbook for the full detail.

Run it locally

cd starter
uv sync                      # Python 3.11 + deps into .venv
cp .env.example .env         # then fill in secrets (below)
uv run python -m app.main    # serves on $PORT (default 8000)
curl -s localhost:8000/health
uv run pytest                # full suite, mocked OpenAI — no key needed
bash scripts/smoke.sh http://localhost:8000 "$SARVAM_TOOL_SHARED_SECRET"

Sarvam tools need a public HTTPS URL — the live one is a cloudflared named tunnel: kaayal.glitchy.systems → localhost:8000. Any tunnel (cloudflared tunnel --url …, ngrok, Tailscale Funnel) works for dev; update KAAYAL_PUBLIC_BASE_URL and the Sarvam tool URLs when it changes.

Canonical runbook: docs/run-local-and-tunnel.md

Sarvam dashboard setup

  1. Confirm the already-provisioned number under Deploy → Phone Numbers. Do not rent a new one.
  2. Create five API tools (voice_reply, list_boats, get_boat, create_booking_request, create_callback_request) — all api_key auth with header X-Kaayal-Tool-Token, 10–15s max wait, an honest failure line.
  3. Paste the Paayal checklist prompt into the agent instructions (it is the only lever over when tools fire) and enable all five tools.
  4. Initial language Malayalam (ml-IN), Malayalam-capable voice.
  5. Deploy → Inbounds → Create Inbound: attach agent + number, widen calling hours to 00:00–23:59 for testing.
  6. Press Test in each tool editor, then place real calls in Malayalam and English — general question, boat question, test request.
  7. Optional — real outbound callbacks: create a second agent ("Paayal Callbacks"), no API tools, variables customer_name, callback_reason, what, request_ref, operator_name, callback_outcome (agent-set). Commit a version, note app_id/version + connection_id, set the SARVAM_* env vars and OUTBOUND_PROVIDER=sarvam. The backend passes context as agent variables and polls the analytics attempts API for connectivity_status + callback_outcome — no webhook to expose.

Full steps, exact request bodies and the Paayal prompt: docs/sarvam-dashboard-setup.md

Onboard an operator (~2 min)

PostStageWhat happens
01dmOperator DMs the Kaayal WhatsApp number (+91 9400354625) — or the owner adds them directly in /admin, skipping to approve.
02formwa-bot collects name → boat name → embarkation, then POST /api/ops/wa_onboard.
03reviewOperator + boat created, approved_at=NULL — pending; no portal access yet.
04approveOwner clicks Approve in /admin → portal link pushed back over WhatsApp. Link is the login; reissue kills the old one instantly.
05boatsOperator adds boats in the portal — each lands pending verification, invisible to callers.
06liveOwner Verify in /admin → live on the site and in list_boats; requests reach the portal, Confirm reveals the customer's contact.
  1. /admin?t=… → Add operator → copy the one-time portal link. The link is their access.
  2. Send it to them however you normally talk (call, WhatsApp, in person).
  3. They add boats on the portal — each lands pending verification, invisible to callers.
  4. You Verify in /admin → live on the site and in list_boats.
  5. Requests reach their portal; Confirm reveals the customer's contact for a direct call-back. Lost link → Reissue in admin (old link dies instantly).

Demo script

/admin → Seed demo data creates two clearly labeled demo operators — one reachable with an available boat, one unreachable with an unavailable boat — so every scenario is walkable without real inventory:

ScenarioShows
Tourist journeyInquire on unavailable boat → consent → callback queued → operator flips available → engine calls (simulated) → inquiry auto-created → operator confirms.
Operator unreachableSame loop triggered by the portal "I'm reachable" toggle.
WhatsApp onboardingDM → bot → pending approval → admin approves → portal link back over WhatsApp.
Safety"Don't call me" opt-outs, retry caps, expiry, 90-day PII anonymization.

WhatsApp sidecar (demo only)

cd starter
docker compose up -d wa-bot   # the wa-session volume keeps the pairing across recreates
docker compose logs -f wa-bot # prints a QR — pair it on the +91 9400354625 phone
# fallback if containers aren't running: cd starter/wa-bot && npm install && npm start

Operators DM that number; the bot walks them through name → boat (name, boat type, boarding point or skip, confirmed with YES/NO) and posts to POST /api/ops/wa_onboard (same tool token). Voice notes are decrypted and transcribed server-side (wa_transcribe, whisper-1). Repeat DMs re-issue the portal link — the old one dies instantly. Boats arrive source=wa-demo, unverified.

Chat commandEffect
REQUESTSLists the operator's pending requests — names shown, customer numbers stay masked until confirm.
REQ-xxxxConfirms the request, unmasks the caller's number, and fires the notify call (demo dialer).
DECLINE REQ-xxxxDeclines; nothing is sent to the caller.
Reply YES/NO to the request pingSwipe-reply shortcut — works only when the quoted message names exactly one REQ id.
PAUSE / RESUMEFlips operator reachability; RESUME fires queued operator_unreachable callbacks.
HELPLists the commands.

Boundary

whatsapp-web.js automates WhatsApp Web — unofficial, ban-able, dies when the paired phone is offline. Production WhatsApp Business API is explicitly deferred.
