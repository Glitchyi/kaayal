Architecture

Three pieces do the work: Sarvam owns the phone call, a small FastAPI service owns the data and the rules, and OpenAI writes short spoken answers — nothing more.

Big picture

Components

The five tools Paayal can call

All five sit behind the same auth dependency — header X-Kaayal-Tool-Token compared with SARVAM_TOOL_SHARED_SECRET via hmac.compare_digest. Wrong or missing → 401; secret unset → 503 service_not_configured.

Sarvam toolEndpointReads / writesReturns
voice_replyPOST /api/voice/reply OpenAI (nothing else) {reply_text, trace_id} — spoken verbatim

create_callback_requestPOST /api/voice/callback SQLite — inserts/updates a CB-… row {…, status, message}; statuses queued · opted_out · rejected. consent_given=false is the opt-out path

Why catalog calls never touch OpenAI

Listings, prices and requests must come from verified rows — not a language model's memory. OpenAI only ever writes opinion text for general questions; structured answers always come from the database. That's what lets Paayal speak real inventory without ever inventing it.

Key flows

A general question → voice_reply

  1. Caller asks something open-ended ("what is a shikara?"). Paayal's hosted LLM classifies it and POSTs {utterance, interaction_id, language}.
  2. Backend checks the tool token, then a fixed-window rate limit (rate_limit_per_minute, default 60) — trips return 429.
  3. OpenAI answers under the Kaayal system prompt with a 12s timeout and a small output-token cap. Failure → honest 502 upstream_unavailable, never a made-up answer.
  4. Reply is whitespace-collapsed, capped at 600 chars, returned with a trace_id. Paayal speaks it.
  5. Log line carries only trace_id, interaction_id, language and latency — never the utterance or the caller's number.

A booking request → operator confirmation

  1. Paayal collects boat, name, callback number, date, group size — then asks for explicit consent before anything is stored.
  2. POST /api/voice/request validates and writes a REQ-… row (status=pending, source=voice). Boat-less requests go to the owner triage queue.
  3. The row appears on the operator's portal and in /admin.
  4. Operator taps Confirm — only then is the customer's name + number revealed — and calls or WhatsApps them directly (wa.me deep links on confirmed requests).
  5. Kaayal never confirms a booking itself; the spoken message only ever says the operator will call.

The callback engine

When a boat is unavailable or an operator unreachable, Paayal offers "I can call you back when that changes." A yes writes a CB-… row; a no writes nothing.

MechanismBehavior
Triggersfire_boat_available / fire_operator_reachable — fired by portal toggles; requeue matching rows and bump trigger_seq.
TickLifespan task wakes every callback_tick_seconds (30s), calls process_due_callbacks. Admin can also force a run.
WindowAttempts only 09:00–18:00 IST; due rows outside the window are rescheduled to the next window start. DEMO_IGNORE_CALL_WINDOW bypasses for demos.
RetriesMax 2 attempts per trigger, ≥61 min apart; no_answer is terminal for that trigger.
Expiry7 days, or before the travel date when one parses.
Outcomeinterested auto-converts to a booking inquiry (source=callback) → same portal flow. not_interested opts the number out.
Opt-out"Don't call me" → consent_given=false cancels every active callback for that number; admin can cancel too.
ProviderSimulatedProvider today — deterministic outcome, script transcript, no dialing. SarvamOutboundProvider exists but raises until approved and configured.

Data model

Five SQLModel tables in kaayal.db. Provenance travels on every row via source; customer PII lives only in request/callback rows and is anonymized after 90 days.

Security & privacy

  • Three auth models, three audiences. Shared-secret header for Sarvam tools; ADMIN_TOKEN for the owner; unguessable portal URLs for operators (hash-only storage, shown once, reissue kills the old link).
  • Bounded input. 16 KB body cap middleware; Pydantic validation returns 400 without echoing input back; rate limit on the one endpoint that costs money.
  • Consent before storage. Customer name/phone is only ever written after an explicit yes — on calls and on the web form. Opt-out is a first-class path, not an edge case.
  • Quiet logs. No utterances, transcripts, phone numbers or secrets in logs — only trace/interaction IDs, outcomes and latencies.
  • PII retention. app/pii.py anonymizes stale request PII at startup (and via scripts/anonymize_pii.py) after 90 days.
  • Honest failure. Upstream errors surface as 502 upstream_unavailable; Paayal's tool-failure line says the service is unreachable. Nothing is faked to sound successful.

Deployment reality

Deliberately small: one uvicorn process, one SQLite file, one cloudflared tunnel, one optional Node sidecar. No cluster, no broker, no P2P.

Known fragility

uvicorn and cloudflared run as unsupervised background processes — they die on reboot or logout. Process supervision (launchd / cloudflared service install) is a pending task in STATUS.md.
